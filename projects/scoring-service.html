DQ Lab · 2023

Scoring Service

Taking a correct-but-slow R→Python port down from 3–5 second response times to under 3 milliseconds.

PythonFastAPIRedisMongoDBNumPy

Challenge

This was the first thing I touched at DQ Lab. The assessment scoring service had started life in R, and the direct port to Python — needed to fit the rest of the production stack — was correct but slow. The use case made that a real problem: a user finishes an assessment, the backend asks this service for a score, and that score has to show up on the portal immediately. There's no loading state budgeted for "the server is thinking."

Architecture & design

The fix wasn't a clever algorithm, it was moving almost everything out of the request path. What's left at request time is just a vectorized calculation over numbers that are already sitting in cache, which is where Python actually gets to be fast.

Approach & key decisions

Caching what doesn't change per request

Rubric weights and normalization values don't change per request, so they get computed once and pulled from Redis instead of being recalculated — or re-fetched from the database — on every single call.

Vectorizing the part that's actually per-request

With the heavy lookups cached, what's left is a vectorized calculation over numbers already sitting in memory — no database round-trip, no row-by-row Python loops.

Decoupling logging from the response

Writing the result to MongoDB for history and dashboards happens after the response goes out, not before, so logging never competes with the thing the portal is actually waiting on.

Result

Response times dropped from 3–5 seconds to under 3 milliseconds.
